# 개인 보드와 그룹 대시보드 아키텍처 v1

## 결론

서비스의 중심은 **개인 보드**다. 누구나 로그인 없이 자기 기기에서 바로 시작하고,
필요한 항목만 선택해 하나 이상의 **그룹 워크스페이스**로 보낸다. 그룹은 개인 보드의
하위 기능이 아니라 별도의 권한·기록·알림 경계를 가진 실행 공간이다.

## 기본 원칙

| 원칙 | 설계 결정 |
| --- | --- |
| 즉시 시작 | 개인 보드는 계정 없이 로컬 저장소에서 열린다. |
| 선택적 공유 | 개인 데이터는 자동 공유하지 않는다. 사용자가 항목과 대상 그룹을 고른다. |
| 그룹별 격리 | 각 그룹의 멤버, 역할, 공지 확인, 질문, 이력은 다른 그룹과 섞이지 않는다. |
| 재시도 안전 | 공유 요청마다 고유 `eventId`를 만들고, 같은 요청을 다시 보내도 팀 업무가 중복 생성되지 않는다. |
| 이력 우선 | 개인 변경 이력과 그룹 발행 이력을 분리해 남기고, 서로의 원문을 복사하지 않는다. |

## 구성

| 층 | 책임 | 현재 구현 / 다음 구현 |
| --- | --- | --- |
| 개인 보드 | 할 일, 메모, 일정, 개인 신호, 개인 이력 | **기기별 DuckDB 정본** |
| 개인 Outbox | 그룹으로 보낼 요약, 대상, 발행 상태, 재시도 | 개인 DuckDB 안의 트랜잭션 Outbox |
| 동기화 경계 | 로그인, 초대 확인, 멤버십 검사, 중복 방지 | Apps Script 웹 앱의 API → 전용 API로 확장 가능 |
| 그룹 워크스페이스 | 업무·공지·질문·일정·읽음·그룹 이력 | 현재 Google Sheets + Apps Script |
| 알림/주기 처리 | 오전 요약, 마감 알림, 주기 갱신 | Apps Script 트리거, 이후 외부 알림 채널을 추가 |

## 데이터 흐름

1. 개인 보드는 기기 안의 DuckDB에 원문을 저장한다.
2. 사용자가 항목을 고르고 제목·요약·그룹·발행 유형을 결정한다.
3. Outbox가 `eventId`와 발행 상태 `queued`를 만든다.
4. 동기화 경계가 로그인한 사용자의 그룹 멤버십과 역할을 확인한다.
5. 그룹 어댑터가 업무·공지·일정 중 하나를 만들고, `eventId`를 그룹 원장에 기록한다.
6. 응답이 오면 개인 Outbox를 `published`로 바꾸고 대상 ID를 저장한다.

실패하면 `queued`를 유지한다. 개인 원문을 삭제하거나 자동으로 다시 발행하지 않는다.

## 최소 데이터 계약

### 개인 기기 — DuckDB 정본

개인 보드는 `personal-board.duckdb` 하나를 정본으로 둔다. 화면은 SQL을 직접 실행하는
로컬 서비스에 붙고, 로컬 서비스만 DuckDB 쓰기 연결을 가진다. 따라서 화면·RAG 작업·그룹
발행이 동시에 일어나도 쓰기는 하나의 트랜잭션 경계에서 직렬화한다.

| 테이블 | 역할 |
| --- | --- |
| `items` | 업무, 메모, 일정, 상태, 마감일 |
| `item_events` | 생성·수정·완료·복구 이력 |
| `outbox_events` | 그룹 발행 전 상태와 `event_id` |
| `sources` | 파일·웹·수동 메모의 출처와 권한 범위 |
| `chunks` | RAG용 청크, 원문 위치, checksum |
| `embeddings` | `chunk_id`, 모델, 차원, 벡터, 생성 시각 |
| `rag_runs` | 질의, 검색 기준, 참조한 `chunk_id`, 사용자 확인 결과 |

직접 SQL은 로컬 콘솔에서 제공한다. 기본은 읽기 전용이며, `INSERT`·`UPDATE`·`DELETE`는
미리보기와 트랜잭션 확인을 거친다. 외부 그룹 API는 이 DB 파일에 직접 접근하지 않는다.

### 개인 기기 엔터티

| 엔터티 | 핵심 필드 |
| --- | --- |
| `PersonalItem` | `id`, `kind`, `title`, `body`, `dueAt`, `status`, `updatedAt` |
| `OutboxEvent` | `eventId`, `personalItemId`, `workspaceId`, `targetType`, `summary`, `state`, `createdAt`, `publishedTargetId` |
| `LocalProfile` | `deviceId`, `displayName`, `preferences` |

### RAG 계약

RAG는 별도 벡터 서비스가 아니라 개인 DuckDB의 `chunks`와 `embeddings`를 함께 사용한다.

1. 원문을 `sources`에 등록하고 청크별 checksum을 만든다.
2. 임베딩 모델·차원을 `embeddings` 메타데이터와 함께 기록한다.
3. 검색은 SQL 필터(날짜, 프로젝트, 비공개 범위)와 벡터 유사도를 결합한다.
4. 답변에는 항상 `source_id`, `chunk_id`, 원문 위치를 남긴다.
5. 근거가 없으면 답변을 만들지 않고 검색 실패로 끝낸다.

개인 RAG 결과는 개인 보드에만 표시한다. 그룹에 보내려면 사용자가 새 요약을 만들고
Outbox에 넣어야 한다.

### Ziphyun 연동 — 선택 어댑터

Ziphyun은 DuckDB·임베딩·어휘/의미 하이브리드 검색을 이미 가진 별도 워크벤치다.
따라서 개인 보드의 정본을 Ziphyun으로 옮기지 않고, 아래 두 개의 선택적 어댑터로 연결한다.

| 방향 | 하는 일 | 금지하는 일 |
| --- | --- | --- |
| 개인 보드 → Ziphyun | 사용자가 선택한 출처 또는 청크를 Ziphyun 프로젝트에 인덱싱 요청 | 개인 DB 전체, Outbox, 그룹 멤버 정보를 자동 업로드 |
| Ziphyun → 개인 보드 | 인용 가능한 검색 결과와 `context:id`를 개인 RAG 결과에 붙임 | Ziphyun 답변을 근거·사용자 확인 없이 그룹에 발행 |

어댑터 요청에는 `source_id`, checksum, 허용한 범위, Ziphyun 프로젝트 ID만 담는다.
원문을 내보낼 때는 별도 동의가 필요하다. Ziphyun 쪽의 프로젝트 격리와 임베딩·검색 기능은
재사용하되, 개인 보드의 권한·삭제·보존 정책은 개인 DuckDB가 결정한다.

### 그룹 워크스페이스

| 엔터티 | 핵심 필드 |
| --- | --- |
| `Workspace` | `workspaceId`, `name`, `ownerId`, `createdAt` |
| `Membership` | `workspaceId`, `memberId`, `role`, `active` |
| `GroupTask` | `taskId`, `workspaceId`, `title`, `ownerId`, `dueDate`, `status` |
| `Announcement` | `noticeId`, `workspaceId`, `title`, `body`, `publishedAt` |
| `PublicationLedger` | `eventId`, `workspaceId`, `targetType`, `targetId`, `actorId`, `publishedAt` |

`eventId`는 그룹 안에서 유일해야 한다. 이것이 재시도 중복을 막는 기준이다.

## 권한 경계

| 행동 | 개인 보드 | 그룹 멤버 | 그룹 리드/관리자 |
| --- | --- | --- | --- |
| 개인 항목 작성·수정 | 가능 | 가능 | 가능 |
| 그룹에 발행 | 대상 그룹의 멤버일 때만 | 가능 | 가능 |
| 공지 게시 | 불가 | 기본값 불가 | 가능 |
| 멤버·역할 관리 | 불가 | 불가 | 가능 |
| 공지 읽음·질문 | 발행 뒤 참여자로서 가능 | 가능 | 가능 |

개인 보드는 로그인 없이 작동한다. 다만 그룹에 처음 연결하는 순간에는 Google 계정 같은
그룹 식별 수단으로 멤버십을 확인한다. 개인 이름을 입력했다고 그룹 권한이 생기지는 않는다.

## 현재 Google Sheets의 위치

현재 시트는 **그룹 워크스페이스 v1의 저장소 겸 운영 원장**으로 한정한다.

- `Tasks`, `Announcements`, `Questions`, `ReadReceipts`, `Schedule`, `Activity`는 그룹 실행 기록이다.
- `Promotions`, `SyncLedger`는 기존 단일 그룹용 발행 대기 구조다.
- 여러 그룹을 지원할 때는 각 그룹을 별도 스프레드시트로 분리하거나, 모든 행에 `workspaceId`를 추가한다.

초기에는 **그룹당 하나의 스프레드시트**를 권장한다. 권한과 데이터 격리가 단순하고,
팀별 관리자도 직접 원장을 확인할 수 있다. 그룹 수가 많아져 운영이 어려워질 때만
중앙 API와 단일 데이터베이스로 옮긴다.

## 단계별 구축

### 1단계 — 개인 DuckDB와 로컬 SQL을 제품의 시작점으로 고정

- `localStorage` 프로토타입을 DuckDB 로컬 서비스로 교체한다.
- 개인 항목, 이력, Outbox, RAG 원장 테이블을 하나의 스키마로 만든다.
- SQL 콘솔은 읽기 전용부터 열고, 쓰기는 트랜잭션 미리보기로 제한한다.
- 그룹 연결 전에도 업무·마감·개인 이력이 완결되게 만든다.

### 1.5단계 — 개인 RAG와 Ziphyun 어댑터

- 파일·메모를 청크화하고 임베딩 모델·차원·출처를 함께 기록한다.
- 개인 DuckDB 검색 결과에 인용 가능한 출처 핸들을 붙인다.
- Ziphyun 연동은 프로젝트별 opt-in으로 만들고, 수출·수입 모두 원문 범위를 화면에서 보여 준다.

### 2단계 — 그룹 연결과 초대

- 그룹 생성, 초대 링크, Google 로그인 기반 멤버십 확인을 추가한다.
- 그룹 선택 후에만 발행 버튼을 노출한다.
- 발행 API는 `eventId`로 멱등성을 보장한다.

### 3단계 — 그룹 운영 자동화

- 오전 요약, 마감 임박, 미확인 공지, 질문 대기를 그룹별로 집계한다.
- 개인 알림은 개인 보드에서, 그룹 알림은 그룹 워크스페이스에서 별도로 설정한다.

### 4단계 — 저장소 교체를 위한 어댑터 분리

- 화면은 `PersonalRepository`, `WorkspaceRepository`, `PublicationGateway`만 사용한다.
- Google Sheets/Apps Script는 `WorkspaceRepository`의 첫 구현체로 둔다.
- 이후 데이터베이스를 바꿔도 화면과 개인 데이터 형식은 유지한다.

## 확인 기준

- 계정이 없는 새 사용자가 오프라인에서도 개인 업무를 만들 수 있다.
- 같은 개인 항목을 두 그룹으로 각각 발행할 수 있다.
- 네트워크 오류 뒤 재시도해도 같은 그룹에 중복 업무가 생기지 않는다.
- 개인 메모 원문은 그룹 시트와 그룹 활동 이력에 나타나지 않는다.
- 그룹에서 만든 업무와 공지는 개인 원장과 그룹 원장에서 각각 출처를 확인할 수 있다.
